```html 啵啵学编程：依赖注入大冒险

🧒 啵啵学编程 🧒

第1话：依赖注入大冒险！
1
🎬 什么是"依赖"？
爸爸
啵啵，玩乐高的时候，你需要什么才能搭出城堡呀？
啵啵
嗯...我需要积木块！还需要轮子和小人！
爸爸
对！这些积木块就是你的"依赖"——没有它们，你就搭不了城堡。

编程也是一样：一个函数要工作，就需要"依赖"其他东西。
⬇️
2
🤔 两种获取积木的方式
爸爸
方式一：自己找积木
你跑到玩具箱前，翻来翻去，找到灰色积木、红色积木...满头大汗！

这就是传统方式：代码自己创建依赖。
啵啵
好累啊...要是换一个玩具箱，我还得重新找...
爸爸
方式二：爸爸递给你
你坐在桌前说"我要搭城堡"，爸爸就把需要的积木递到你手上。

这就是"依赖注入"——你需要什么，别人递给你！
💡 核心区别：谁来找积木？
方式一：你自己找（函数内部控制依赖）
方式二：别人递给你（依赖从外部注入）
👉 这个"从自己找变成别人递"就叫 控制反转（IoC）
⬇️
3
🧪 pytest 是怎么"递积木"的？
pytest君
啵啵，看我的魔法！你只要在参数里写"积木"，我就自动找到同名fixture递给你！
import pytest

@pytest.fixture
def 积木():
    print("爸爸：给你红色积木！")
    yield "红色积木" # 递给你
    print("爸爸：积木用完了，我收回去啦")

def test_搭城堡(积木): # 参数名=fixture名
    print(f"啵啵：我用{积木}搭了一个城堡！")
    assert 积木 == "红色积木"
啵啵
哦！`yield` 就是爸爸递过来的手，`yield` 后面的代码是爸爸收回积木！
🎯 pytest 的依赖注入公式：
fixture 名 = 参数名 → pytest 自动匹配并注入！
⬇️
4
📦 三种"递积木"的方式（作用域）
递法 乐高类比 pytest 代码 什么时候用？ 每次都递新积木 你要一块，爸爸给你一块全新的。再要一块，再给一块新的。 scope="function" 需要干净的积木，不能沾上上次的颜色（测试隔离） 整个搭建过程只递一次 爸爸说："这盒积木你搭城堡全程用，我不反复递了。" scope="class" 多个测试共享同一套积木（共享数据库连接） 今天下午只递一次 爸爸说："这盒特殊积木，今天下午只给你一次，后面都用同一盒。" scope="session" 整个测试过程只创建一次（昂贵资源，如启动服务器）
⬇️
5
🧩 进阶知识①：爸爸不仅能递积木！
📚 原来如此！ 契约（接口）的力量

啵啵长大了才明白：爸爸不仅能递积木，还能递任何"能拼的东西"——磁力片、雪花片、木头块...只要它们符合"能拼"的约定！

老师
啵啵，你现在学多态了！依赖注入最厉害的地方是：
你只定规矩（接口），不管具体实现！
# 啵啵只关心"能发送消息"，不关心怎么发
def 发通知(用户, 发送器): # 发送器只是个"约定"
    发送器.发送(用户, "你好")

# 爸爸可以递任何符合约定的东西：
class 邮件发送器:
    def 发送(self, 用户, 消息):
        print(f"📧 发邮件给{用户}: {消息}")

class 微信发送器:
    def 发送(self, 用户, 消息):
        print(f"💬 发微信给{用户}: {消息}")

class 狼烟发送器: # 甚至可以用狼烟！
    def 发送(self, 用户, 消息):
        print(f"🔥 点狼烟给{用户}: {消息}")
💡 递积木的升级理解：
小时候以为"爸爸递积木"
长大后明白"爸爸递任何符合约定的东西"
👉 这叫 面向接口编程
⬇️
6
🏗️ 进阶知识②：现实中的"递积木"有多复杂？
📚 原来如此！ 依赖树（DI 容器）

真实项目里：一个依赖需要另一个依赖，另一个又需要第三个...像俄罗斯套娃一样！ 所以需要DI 容器（比如 Spring、Angular）来当"超级爸爸"，自动管理所有递东西的规则。

电脑
看这个依赖链：
🔗 UserService → UserRepository → Database → Config
一共4层！一个要一个，一个又要下一个...
# 真实世界的依赖组装（没有容器时的手动噩梦）
config = Config()
db = Database(config) # db 依赖 config
cache = RedisCache()
repo = UserRepository(db, cache) # repo 依赖 db 和 cache
email = EmailService()
logger = Logger()
service = UserService(repo, email, logger) # service 依赖前三个

# 有了 DI 容器：
# @Autowired UserService service; ← 一行搞定！容器自动组装！
🏗️ DI 容器 = 超级爸爸
你只需要说"我要UserService"，容器自动帮你把所有嵌套依赖都创建好！
⬇️
7
♻️ 进阶知识③：用完要收回去！（生命周期管理）
📚 原来如此！ 资源泄漏的危害

爸爸递积木，啵啵用完爸爸收走。但如果爸爸忘了收呢？积木越堆越多，玩具房就爆炸了！ 编程中叫"内存泄漏"——数据库连接不关、文件不关，系统就崩溃了。

爸爸
yield 后面的代码就是"收回积木"，千万不能忘！
@pytest.fixture
def 数据库连接():
    conn = 创建连接() # 递积木
    yield conn
    conn.关闭() # ⚠️ 必须收回！忘了就内存泄漏！
⚠️ 忘记 yield 后面的清理代码 = 玩具房越来越乱 = 系统崩溃
⬇️
8
⚖️ 进阶知识④：什么时候该递新积木？什么时候共享？
📚 原来如此！ 作用域的性能权衡

100个测试，每次都创建新数据库连接？太慢了！ 但如果100个测试共享同一个连接，前面测试改的数据可能影响后面的测试？污染了！ 这是一个需要权衡的问题。

场景 选"每次都递新积木" 选"共享一盒积木" 测试需要独立数据 ✅ 互不干扰 ❌ 可能污染 创建成本很高 ❌ 非常慢 ✅ 只创建一次 需要修改共享状态 ✅ 安全 ⚠️ 需要小心
🎓 核心权衡：隔离性 vs 性能
默认用 function 作用域（最安全），性能出问题再优化！
⬇️
9
🕵️ 进阶知识⑤：小心"偷偷找积木"！
📚 原来如此！ 隐式依赖的危害

表面上说"爸爸递积木"，但代码里偷偷引用了全局变量——这叫隐式依赖。 测试时发现依赖注入"失灵了"，其实就是因为有人偷偷自己找了积木！

# 看起来用了依赖注入...
def 发送欢迎邮件(用户id, 邮件服务):
    用户 = 数据库.查询(f"SELECT * FROM users WHERE id={用户id}")
    # ↑↑↑ 等等！数据库从哪来的？这是隐式依赖！
    邮件服务.发送(用户.邮箱, "欢迎")
老师
真正的依赖注入：所有依赖都通过参数传入！
不要偷偷引用全局变量，否则测试时会很痛苦...
🚫 规则：函数体内用到的所有外部东西，都应该通过参数（依赖注入）获得！
```
